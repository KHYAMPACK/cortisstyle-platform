# 05 — Owner panel & commerce rails

**What this is:** the owner-facing product/order management UI (`/tr/panel`) and the money-moving path behind it — cart, checkout, shipping, discounts, payments. This is the highest-traffic surface for both bugs and future feature work, and the one place where "generic vs. fashion-specific" is still genuinely unresolved in several files — read the caveat below before editing panel product forms.

## Owner panel structure

Routes live under `src/app/tr/panel/`, gated by owner auth (`src/lib/tr/ownerAuth.ts`) and Bearer + `owner_user_id` on the API side. What an owner sees is gated by `catalog_profile` capability flags (`src/lib/tr/catalogProfiles/registry.ts` — `showProductsNav`, `showStockNav`, `allowProductRoutes`, `pdpLayout`, `skipStockValidation`, `skipInventoryDecrement`, etc.), not by slug checks.

**Who can open a store's panel:** its owner (`tr_boutiques.owner_user_id`, one per store), anyone whose **confirmed e-mail** is in that store's admin list (`tr_boutique_admins`, built 2026-10-18; same access as the owner, that one store only; `lib/tr/panel/boutiqueAdmins.ts`, `listBoutiquesForUser` in `ownerAuth.ts`), and platform staff (`TR_PANEL_STAFF_EMAILS`, every store — not for client teams). Manage admins with `scripts/boutique-admins.mts --slug <slug> --list|--add a@x.com,b@y.com|--remove a@x.com`; they can be added before they have an account and get access when they sign up and confirm the address. Every admin also receives the new-order e-mail. Needs `supabase/patch_tr_boutique_admins.sql` (applied by hand); without it the app simply finds no admins. No panel screen for this yet.

Product management pages: `urun/yeni` (Basit or Gelişmiş; Gelişmiş is "Yakında" for owners, open to staff), `urun/yeni/basit`, `urun/yeni/gelismis` and `urun/[id]` (edit) — all in the full-screen editor layout and all the same editor, `TrProductEditor` (see "The product editor"), where the product's kind is picked in an Ürün türü card like its categories (`TrPanelKindPicker`); the old create addresses (`urun/yeni/moda[/tek-parca]`, `urun/takim`, `urun/toplu`) redirect to `urun/yeni` — plus `urunler` (list) and `stok` (stock table). Order pages: `siparisler` (list/detail), `siparisler/yeni` (Sipariş Oluştur) and `taslaklar` (Taslaklar) — see "Manual orders & drafts". Customer pages: `musteriler` (list, `yeni`, `[id]`, `[id]/duzenle` — see "Customers"). `ayarlar` is boutique settings (brand, WhatsApp, IG, contact — all writing straight to `tr_boutiques` columns).

**Important caveat for anyone editing these:** `TrOwnerGuidedPhotoUpload.tsx`, `TrOwnerStorePreview.tsx`, `TrOwnerProductListPage.tsx`, and `TrOwnerStockPage.tsx` are large files (several are 1500+ lines) that interleave **generic** product fields (title, price, stock, images) with **garment-specific** UI (size charts, construction chips, category taxonomy) in the same component. This is known, deliberate technical debt from the fashion-module extraction (see [06-fashion-module.md](./06-fashion-module.md)) — splitting them cleanly is a bigger, riskier job than a file move and was deferred on purpose. Don't assume everything in `src/components/tr/panel/` is generic just because it's not under `src/components/tr/fashion/panel/`.

## Panel shell & navigation (how pages load — follow this for every new page)

**The shell mounts once.** `TrPanelShell` (`src/components/tr/panel/TrPanelShell.tsx`) is rendered by `src/app/tr/panel/layout.tsx`. It owns sign-in, the boutique list, the sidebar / mobile chrome, order alerts, and the leave-guard and restyle-session providers, and it stays mounted while the user moves between panel pages — only the page slot below it changes. It used to be mounted *by each page* (via `TrOwnerPanelGate`), which tore the sidebar down, showed a skeleton and re-fetched the boutique list on every click; that was the whole "not instant" feeling. A page must never mount its own shell.

**Pages read the shell, they don't build it.** `TrOwnerPanelGate` is now only a consumer: `<TrOwnerPanelGate>{({ activeBoutique }) => …}</TrOwnerPanelGate>` hands the page the active boutique, the boutique list, `isStaff` and `setActiveBoutiqueId` (the same shape as before, so pages didn't change). Add a new panel page as a route under `src/app/tr/panel/` that renders a client component wrapped in it — nothing else.

**How a click stays fast:**
1. **Prefetch the whole route.** Panel routes are dynamic, so `prefetch="auto"` only fetches down to the loading boundary and the click still waits on the server. Nav links use `prefetch` (full route, cached 5 min by the client router — no global `staleTimes` change, so the storefront's no-cache behavior is untouched). In-page links use `TrPanelLink` (`TrPanelLink.tsx`), which arms the same full prefetch on hover, focus or touch so a long list doesn't prefetch every row on load. **Use `TrPanelLink`, not `next/link`, for panel links.** Prefetching only runs in production builds — judge speed on `npm run build && npm start` or a deploy, not on `npm run dev`.
2. **Optimistic active state.** `TrPanelNavLinks` moves the active pill on click, before the route commits. It is tied to the path it was clicked from, so it stops applying on its own once the real path changes. A navigation the leave guard blocks never reaches the click handler (the guard stops it in the capture phase), so the pill can't get ahead of a blocked click.
3. **No exit animation.** `app/tr/panel/template.tsx` re-mounts per navigation and replays a 140 ms opacity-only fade (`.tr-panel-enter` in `globals.css`); nothing waits for the old page to leave. Opacity only — a transform on that wrapper breaks `position: sticky` descendants (list filters).
4. **Instant fallback.** `app/tr/panel/loading.tsx` shows a skeleton in the page slot the moment a navigation starts if the route wasn't prefetched; the shell stays put.
5. **Data is cached separately** in `src/lib/tr/panel/ownerCache.ts` (20 s, in-flight de-duplication, prefix invalidation). Fetch through `cachedOwnerFetch` so a revisit renders immediately.

**Menu groups.** The sidebar list is `TR_PANEL_NAV` in `src/lib/tr/panel/panelNav.ts`: each entry is a link or a *group* (an expandable heading with pages nested under it — Ürünler → Ürünler, Stok). Today only Ürünler is a group, mirroring the reference admin; further Ürünler sub-pages (tanımlamalar, fiyat listesi, barkod etiketi, …) are added one at a time as real pages, not as "coming soon" placeholders. **To add a sub-page:** add the route under `src/app/tr/panel/`, add a child to the group in `TR_PANEL_NAV`, and hide it per vertical in `panelNavForProfile` if some `catalog_profile` shouldn't see it (a group whose children are all hidden disappears). Group headings are not links; a group opens itself when you are on one of its pages, a manual toggle lapses on the next navigation, and when the rail is collapsed the heading's pages open in a hover/click flyout (`TrPanelNavGroup.tsx`). The mobile tab bar uses `flattenPanelNav(...)`, so it still shows the first four links in order.

**Sidebar.** Collapses to a 64 px icon rail (state remembered in `localStorage` via `panelSidebarState.ts` → `usePanelStoredFlag` in `panelStoredFlag.ts`, read with `useSyncExternalStore` so hydration stays clean; reuse that hook for any other remembered on/off preference). The active pill and accent bar slide between items (framer-motion `layoutId`, scoped per instance). Nav rows and footer actions share `panelSidebarRowClass` in `panelUi.ts`, so hover/focus/spacing can't drift. The shell publishes the current width as `--panel-sidebar-w` (and the mobile tab bar height as `--panel-tabbar-h`); anything positioned against the chrome (the wizard's sticky action bar) must use those variables, never a hard-coded 232 px / 3.5rem — both are 0 on editor pages.

**Editor pages.** Anything that creates or edits one thing (a product today; tanımlamalar, fiyat listesi, … later) uses the full-screen editor layout instead of the sidebar layout: `TrPanelEditor` (`TrPanelEditor.tsx`) is a dark top bar (back arrow, `Ürünler › Ürünü düzenle` crumbs, optional centred subject, an actions slot) over a centred column. Inside it: `TrPanelEditorTabs` (sticky section tabs that scroll to a card and follow the scroll), `TrPanelEditorCard` (titled card with an (i) hint; give it an `id` for a tab), and `TrPanelEditorActions` (portals buttons or a save indicator into the top bar from anywhere below — the product form uses it for its autosave status). Tabs and cards are optional; a wizard just drops its content into the column. **To make a route an editor page,** add its pattern to `PANEL_EDITOR_ROUTES` in `panelNav.ts` (tested in `panelNav.test.ts`); the shell then hides the sidebar, mobile header and tab bar for it (they stay mounted, only `hidden`, so going back is instant) and zeroes `--panel-sidebar-w` / `--panel-tabbar-h`. The route must render inside `TrPanelEditor` or the user gets no way back. `urun/takim` and `urun/toplu` are wizards that keep the normal chrome and are excluded from the pattern. Tab highlighting is `activeSectionIndex` in `src/lib/tr/panel/editorScrollSpy.ts`.

**Back links — an editor page returns to where you came from.** The back arrow and first crumb of an editor page go to the page it was opened from, not always to its list (`Müşteri Detayı › Sipariş #1001`). A link from one panel page to another goes through `withPanelOrigin(href, fromPath)` (`src/lib/tr/panel/panelOrigin.ts`), which adds `?from=<path>`; the editor page takes its back target from `usePanelBackTarget({ href, label })` (its usual parent as the fallback) and uses `usePanelSelfPath()` as the `from` on its own outgoing links, so a chain of pages unwinds one step at a time. `from` is accepted only if it points inside `/tr/panel`, and the crumb's label comes from the list in `panelOrigin.ts` — never from the URL — so to make a page nameable as an origin, add it there. When an order is opened from somewhere other than the orders list, Önceki / Sonraki (which walk that list) give way to **Kapat**. **Rule for new pages:** links to an editor page use `withPanelOrigin`, and editor pages use `usePanelBackTarget`. Today the order and customer pages do (the order's customer name and the customer's order rows link to each other this way); the product editors still always go back to Ürünler and should adopt it.

**List pages.** `TrOwnerProductListPage` is the reference: title + primary "Ürün ekle" (extra ways in — Takım yükle, Toplu ekle — sit in a `TrPanelPopover` menu), search + a Filtre popover, a read-only `TrPanelDataTable` (`contained={false}`; the whole row opens the editor via `onActivate`), client-side pagination in the footer, and the bulk bar for selections. Editing happens in the editor, not inline in the table.

**Saving — one model for the panel** (decided 2026-09-24; helpers in `src/lib/tr/panel/saveModel.ts`). There are three kinds of interaction and each has one rule:

1. **Forms** — editor pages, drawers, settings-style pages: **manual save**, dirty tracking, and a confirmation when leaving with unsaved edits. **No autosave.** In an editor: put `<TrPanelEditorSave dirty saving saved requireDirty onSave />` in the page (status text + **Kaydet** in the top bar, and **Ctrl/Cmd+S**) and call `useUnsavedChangesGuard(id, dirty)` (`TrOwnerLeaveGuard.tsx`). Leaving the page (sidebar, back arrow, breadcrumb, links) opens a centered dialog with the standard sentence (`UNSAVED_CHANGES_MESSAGE`: "Yaptığınız değişiklikler kaydedilmemiştir. Çıkmak istediğinize emin misiniz?", **Hayır** / **Evet**); reloading or closing the tab shows the browser's own prompt. The browser's Back button is *not* intercepted (the app router can't), which is an accepted gap. A failed save keeps the form dirty and shows the error; after a successful save you stay on the page (a create redirects to the new item's edit page).
2. **Actions** — one-click state changes (order status, "ödendi", invoice status, hide / delete, bulk bar): apply immediately, ask first only when destructive or irreversible, and show the result. They are not "saving" and don't use the guard.
3. **Inline table edits** — a spreadsheet-like screen (Stok today, Fiyat Listesi later): a pending-changes bar with Kaydet / Vazgeç plus the same guard. Not built yet; the Stok page still saves per cell and is untouched (it sits on the older size model).

**Products are added and edited in one editor** (foundation plan F3, 2026-10-02; the fashion editor, the create wizard, Toplu ekle and Takım are deleted). It follows this model: Kaydet, the leave guard, toasts; Durum is Satışta / Gizli, and sold follows stock. Products are added by hand (the AI pipeline is parked, `docs/ai-pipeline-v1.md`). Products made earlier by the AI keep their packshot / model-shot gallery; the editor shows it read-only with a "Fotoğrafları düzenle" button that turns the shop's current gallery into a plain photo list (saved with Kaydet, `features.manualListing = true`). Ayarlar saves manually but has no exit guard yet.

**Messages — toasts** (decided 2026-09-25). What just happened is reported in one way across the panel: a toast at the **bottom center** (white card, coloured round icon, one line, ✕). Call `toast.success("Ürün kaydedildi.")`, `toast.warning(…)` or `toast.error(caughtError, "Ürün kaydedilemedi.")` from `src/lib/tr/panel/toast.ts` — from any handler or library code, no hook. `toast.error` takes a message or the caught error (an `Error`'s message is used, else the fallback). `TrPanelToaster` renders them and is mounted **once in `TrPanelShell`**, which stays mounted across pages, so a toast raised just before a redirect (create → edit page) is still there on the next page; that replaced the old `sessionStorage` hand-over notices. **Rules.** *Toast:* the result of an action (saved, created, deleted, duplicated, status changed, bulk action, upload) and its failure, and the problem a Kaydet press finds in the form (the Kaydet button sits in the top bar, far from an inline box that may be scrolled away). *Stay inline:* a page that failed to load (with retry), a state of the page (empty list, "adres eksik"), a live hint next to a field (character count, why Uygula is disabled), and anything the user must read to continue. *Not a toast:* questions ("Silinsin mi?", "Çıkmak istediğinize emin misiniz?") are the confirm popover and the unsaved-changes dialog. **Behavior:** success stays 4 s, warning 6 s, error 8 s; at most 3 at once (a new one pushes the oldest out); the same message already showing just restarts its timer; several toasts sit as a pile, the newest in front, and **hovering (or focusing) the pile spreads them out and holds every timer** until the pointer leaves; errors are announced to screen readers immediately (`role="alert"`), the rest politely. **Wording:** one Turkish sentence in the past tense with a period ("Ürün silindi."), no "başarıyla", no raw exception text; a failure says what failed and, when useful, what to do ("Ürün kaydedilemedi. Bağlantınızı kontrol edip tekrar deneyin."). The rules and timers are pure and tested (`toast.ts`, the pile geometry in `toastStack.ts`). Migrated so far: the product editor, the category editor, Varyant Türleri (page and drawers), the Ürünler list actions, Siparişler (list bulk actions, the order page, the manual order editor and its address/shipment drawers) and the customer edit page (including the "e-posta kullanımda" case, whose toast carries a "Müşteriyi aç" action button — see `ToastOptions.action` in `toast.ts`); **other pages (Stok, Ana Sayfa, Faturalar, Orijinaller, İndirimler) still show inline boxes (`panelErrorClass`) and move over as their owners touch them.**

**Drawers.** `TrPanelDrawer` is the right-hand slide-over for creating or editing a small thing in place (a variant type, a brand, a category…). It is a form, so it follows rule 1: pass `dirty`, `saving`, `onSave`; **Vazgeç, the ✕, Esc and a click on the backdrop** all go through `TrPanelConfirmPopover` (the ikas-style popover over the button: warning icon, the standard sentence, Hayır / Evet) when `dirty`, and close directly otherwise. Ctrl/Cmd+S saves; Tab stays inside; focus returns to the trigger; the page behind doesn't scroll. The caller closes the drawer when its save succeeds. Every open is a fresh session (nothing carries over). The drawer is portaled to `<body>`, which is why the accent colors are also written to `:root` (`syncPanelAccentVarsToDocument`). `TrPanelConfirmPopover` is reusable for any small yes/no (delete a row, discard a draft).

**Product kinds, not product types.** Since F3 a product's *kind* (Ürün türü, `tr_products.kind_id`, see "Ürün türleri and Özellikler") decides its Özellikler fields; `tr_products.product_type` is still written (`simple`, or `advanced` for a product with variants; old products keep `fashion`) but nothing chooses an editor by it any more. `advanced` (a product with variants) is staff-only (`urun/yeni/gelismis`, and a staff card in the kind chooser) until the shop can sell variants (F5).

**Size tables** (`TrOwnerSizeChartStock`, the product editor's Stok card for every product without variants) offer the boutique's **Beden types** (variant types marked `size`) through `useOwnerSizeSources`; a boutique with none gets the built-in lists (XS–3XL, 24–40 + 42–52). Products still store their own labels (`sizes`, `size_stocks`), so the storefront is unaffected. A draft or an old product on a built-in list is moved onto the matching type (`resolveSizeSourceId` / `detectSizeSourceId` in `sizeSources.ts`). The editor and the **Stok page keep exactly a product's own sizes** (nothing is added on save); a new product starts from the whole list of the size type its kind starts with.

**Shared product fields.** `TrPanelProductFields.tsx` holds what every product editor shares: `TrPanelProductTitleField`, `TrPanelPriceField`, `TrPanelProductVisibilityField` (Satışta / Gizli; sold follows stock), `TrPanelProductStoreLink` ("Mağazada gör") and `TrPanelProductDeleteCard`. Use them rather than copying markup into a new editor.

**The product editor** is `TrProductEditor` (create and edit, every product): cards Temel bilgi (ad, Teslimat Fiziksel/Dijital, Satış / İndirimli / Alış fiyatı, Birim fiyat, durum), Medya, Varyant (products with variants), Ürün türü (`TrPanelKindPicker`: empty state, a drawer to pick from, Değiştir / Kaldır; picking one on a new product also applies its suggested category and size type), Özellikler (the kind's fields, `TrProductAttributesFields`, two per row: a searchable box per choice field (`TrPanelComboboxField`, typing one's own value where the field allows it), a line or a box for text; a stored value outside the options stays the value; required fields are checked on Kaydet), Ürün detayı (Marka, Etiket, Google ürün kategorisi, Tedarikçi, the category picker, rich-text Açıklama), Envanter (SKU, Barkod, Kargo desi, HS kodu), Stok (the size table, or the variants' total), Renk grubu (link separate colour products; until F6), Lokasyon (read-only "Ana adres" from Ayarlar → Adres), SEO, plus a delete card.  It saves explicitly (Kaydet in the top bar) and registers an `unsaved` leave guard. The form rules (price model, sizes, AI-made gallery, kind, validation, payloads) are pure functions in `src/lib/tr/panel/productForm.ts` with tests; the patch sends `features` whole (values of the store's own fields live there under their keys and survive `sanitizeProductFeatures`; `productKinds/featureValues.ts`) and `kindId` only when it changed. **Owner-only data** (Alış fiyatı) lives in `tr_product_private`, not on `tr_products`, because `tr_products` has a public SELECT policy on every column: the owner API returns it next to the product (`private`), and it must never be added to `TrProduct` or a storefront column list. Dijital is stored but informational — such a product still goes through normal checkout and shipping.

**Product details** (`supabase/patch_product_details.sql`, manual, idempotent, apply `patch_product_types.sql` first). Columns on `tr_products` (public-safe): `description_html`, `brand`, `tags text[]`, `google_category`, `sku`, `barcode`, `desi`, `continue_selling_when_out_of_stock`, `unit_price_enabled` / `unit_amount` / `unit_type`; on `tr_product_private` (owner-only): `supplier`, `hs_code`. Types: `TrProductDetails` (`TrProduct`, `CreateTrProductInput` and `UpdateTrProductInput` extend `Partial<>` of it), `TrUnitPrice`, and `TrProductPrivate` now also carries `supplier` / `hsCode`. **One rule set:** `readProductDetailsBody` (`src/lib/tr/productDetails.ts`) validates a request body and the editor calls the same function, so limits and formats can't drift; the API routes (`products/route.ts`, `products/[id]/route.ts`) read details with it, **sanitize the description on every write** (`sanitizeRichHtml`, `richTextSanitize.ts`, `sanitize-html`) and derive the plain `description` from it (`richHtmlToPlainText`, `richText.ts`, which is dependency-free and safe for the browser). The DB side is in `catalog/productDetailColumns.ts` (`detailRow`, missing-column rules): detail values are only sent when non-default (create) or touched (update), so a database without the patch still saves everything else, while a real value aimed at a missing column fails with a message naming the patch instead of vanishing. Reads are `select *`, mapped by `mapProductDetails`. `getProductPrivateAdmin` / `saveProductPrivateAdmin` handle the supplier / HS columns the same tolerant way, and the duplicate action now copies details, private data and categories (not SKU / barcode). **Nothing on the storefront reads these fields yet** (storefront freeze, see the plan): the product page, Google feed, checkout and carrier labels ignore them, and the cards say so. Shared UI: `TrPanelRichTextField` (Tiptap; load it with `next/dynamic` and `ssr: false`, it reads `initialHtml` once and reports edits through `onChange`; content styles are `.tr-rich-content` in `globals.css`), and `TrPanelCreatableSelect` / `TrPanelTagsField` (type a value or pick one already used; suggestions come from `GET /api/tr/owner/products/facets` via `useOwnerProductFacets`, a card holding them needs `allowOverflow`). Unit prices are in `productUnits.ts` (`unitPricePerReference`).

**Variant types (Tanımlamalar → Varyant Türleri)** (`supabase/patch_variant_types.sql`, manual, idempotent, service-role only tables). A variant type is a named option a boutique defines once (Renk, Beden…): `tr_variant_types` (name unique per boutique ignoring case, `selection_style` `list` | `swatch`, `sort_order`) and `tr_variant_type_values` (label unique per type ignoring case, `hex`, `image_url`, `sort_order`; deleting a type cascades). Products will pick types and values from here (Gelişmiş, M7b); nothing outside the panel reads them yet. Rules are pure and tested in `src/lib/tr/variants/`: `typeRules.ts` (`readVariantTypeBody` validates the API body **and** the drawer, limits 40-character names, 100 values, 50 types; a swatch value needs a colour or picture, a list type drops them; `planValueChanges` diffs stored and submitted values), `typeForm.ts` (drawer form state, adding/pasting values, reordering) and `types.ts` (client-safe types). The DB side is `src/lib/tr/catalog/variantTypes.ts`, exposed at `/api/tr/owner/variant-types[/id]` and `/variant-types/import`. **Value ids are stable:** a submitted value keeps its stored row when its `id` matches (rename, reorder, recolour all update in place); values without an id are inserted, missing ones deleted, and a rename that would collide with another value's current label (a swap) goes through temporary labels. **Roles:** a type can be marked as a **Beden** (`role = 'size'`) or **Renk** (`'color'`) type in the drawer ("Kullanım"; `supabase/patch_variant_type_roles.sql`). The fashion panel's size tables offer the boutique's size types (see `docs/fashion-beden-kategori-plan.md`, S1). **Import instead of seeding:** `POST …/import` ("Hazır bedenleri içe aktar") creates the built-in size types, Beden (XS–3XL) and Pantolon bedeni (24–52), for a boutique that has no size type yet (`importableSizeTypeInputs`). Renaming values of a Beden type that products still use offers to rename them on those products too (`sizeRenames.ts`, `POST …/[id]/rename-sizes`; stock unchanged). The old import from `size_presets` / `color_presets` and the unused `boutiques/[id]/options` API were removed (both columns were empty everywhere); the columns stay in the database. **In use:** a type used by a product (`tr_product_options`) and a value used by a variant (`option_value_ids`) can't be deleted or removed (409 with the product count), and the page's Ürünler column counts products per type. The editor UI is `TrVariantTypeDrawer` (built on `TrPanelDrawer`; reusable from a product editor) and the page is `TrOwnerVariantTypesPage`.

**Product variants (Gelişmiş ürün)** (`supabase/patch_product_variants.sql`, manual, idempotent; apply `patch_variant_types.sql` first). `tr_product_options (product_id, type_id, sort_order)` lists the option types a product uses (a used type can't be deleted: `on delete restrict`); `tr_product_variants` holds one row per combination: `option_value_ids uuid[]` (one value id per option, in option order, unique per product), `sku`, `barcode`, `price_kurus` (null = inherits the product's price and discount), `stock`, `images` (a subset of the product's images), `active`, `sort_order`. Both tables are service-role only until the storefront sells variants (M7c), and `tr_products.stock` is kept as the sum of the active variants' stock. **A variant is its combination, not its row:** `planVariantChanges` (`src/lib/tr/variants/productVariantRules.ts`) matches submitted rows to stored ones by the joined value ids, so a save updates rows that survive (their ids stay), inserts new combinations and removes the rest; changing the option types changes what a combination is, so every row is replaced. Rules are pure and tested: `productVariantRules.ts` (`readVariantsBody` validates the API body **and** the editor, max 3 types / 100 variants, price / stock / SKU / barcode limits, `generateCombinations`, `sumActiveStock`) and `variantForm.ts` (form rows, `applySelection`, `applyBulk`, `selectionProblem`). The DB side is `src/lib/tr/catalog/productVariants.ts` (`getProductVariants`, `saveProductVariants` checks that every type is the boutique's and every value belongs to its option, `copyProductVariants`). The product routes take `variants: { typeIds, rows }` on create and update (`undefined` leaves them alone, an empty list clears them), read them back on `GET urun/[id]` (Gelişmiş products only), override the stock with the active sum, and the duplicate action copies them. Reading is tolerant of a missing patch; saving real variants without it fails with a message naming the patch. **UI:** `TrProductVariantsCard` (option summary, Toplu düzenle, the table) and `TrVariantPickerDrawer` inside `TrSimpleProductEditor` when the product is `advanced`; variants live in the product form (`SimpleProductFormState.variants`) and save with Kaydet. **Not built yet:** anything on the storefront (M7c: cart, checkout, inventory, order items, product-page selectors, feed, Stok page), a per-variant compare-at price and cost.

**SEO card and product slugs.** `TrPanelSeoCard` (`TrPanelSeoCard.tsx`) is the shared SEO section: slug, Sayfa Başlığı, Açıklama, Gelişmiş (noindex, canonical path) and a live search-result preview. A page owns the state as a `TrSeoFormValue` and passes what the preview needs (`entityName`, `urlPrefix` from `storeProductUrlPrefix`, `suggestedSlug`); `seoFromForm` / `seoToForm` (`src/lib/tr/seo/seoFields.ts`) convert to and from the API shape. Data: `tr_products.slug` (real column, unique per boutique, optional) and `tr_products.seo` jsonb (`{ title, description, noindex, canonical }`), plus `tr_slug_redirects` (old slug → product; service role only) — `supabase/patch_product_seo.sql`, manual, idempotent. Rules live in `src/lib/tr/seo/slug.ts` (Turkish folding, `-2/-3` uniqueness, never id-shaped) and `src/lib/tr/catalog/productSlug.ts` (DB side). **A new Basit ürün gets a slug from its title unless the owner sets one; garment products and every existing product keep no slug**, so their URLs and metadata are untouched. Renaming a slug records the old one so it redirects (`permanentRedirect`; inside this route's streaming boundary Next emits a client-side redirect, and a true edge-level 308 is part of the planned Store URLs work). All public URL building goes through `src/lib/tr/seo/storeAddress.ts` so the planned subdomain/canonical-host work only changes that file and the proxy.

**Categories and Tanımlamalar** (`supabase/patch_categories.sql`, manual, idempotent). Every boutique uses its own categories (F1, 2026-10-02; `tr_boutiques.category_mode` is still in the DB but no longer read): the picker in the Basit and fashion editors, the category filter, labels and "Kategori ekle" bulk action in Ürünler, Stok chips, order lines and dashboard top sellers all read `tr_categories` (`useOwnerCategories` / `useOwnerCategoryName`). A new boutique gets its profile's starter tree and product kinds at creation (`catalog/starterDefinitions.ts`). **Ürün türleri and Özellikler** (F2, `supabase/patch_product_kinds.sql`): `tr_product_kinds` (what a product is: its fields, starting variant types, suggested category, `system_key`), `tr_attribute_definitions` (a field: `key` in `tr_products.features`, label, `text`/`textarea`/`choice`, options, `allow_custom`) and `tr_product_kind_attributes` (a kind's fields in order, optional narrower options); `tr_products.kind_id`. Pages under Tanımlamalar, a Tür column / filter / "Tür ata…" in Ürünler; rules in `src/lib/tr/productKinds/`, DB in `catalog/productKinds.ts`, API at `/api/tr/owner/product-kinds[/id|/import|/assign]` and `/api/tr/owner/attributes[/id]`. "Hazır türleri içe aktar" copies the fashion template (`fashion/kindTemplate.ts`) and files products by category. Nothing on the storefront or in the editor reads kinds yet (F3). Data: `tr_categories` (unlimited depth via `parent_id`, unique slug per boutique, `seo` jsonb) and `tr_product_categories` (a product has many, exactly one `is_primary`); `tr_products.category` is kept equal to the primary category's slug so the list filters, the feed and the storefront keep working. Still open: a category's description is plain text until the rich-text editor exists.

## Customers (Müşteriler)

A boutique's customers are a real table, **`tr_customers`** (`supabase/patch_tr_customers.sql` — **apply it before using the page**; idempotent, includes a backfill from existing orders). One row per (boutique, lower-cased e-mail): name, e-mail, phone, a private note, and an `addresses` jsonb array (title, recipient, Turkish address fields, default flag). RLS is on with no policies and `anon`/`authenticated` are revoked — like every owner table it is reached only through the service role behind `requireOwnedBoutique`. `tr_orders.customer_id` (nullable, `on delete set null`) links an order to its customer; orders still carry their own name/e-mail/phone snapshot, so deleting a customer never touches order history.

**Who becomes a customer:** whoever places an order. `createOrderAdmin` calls `ensureCustomerForOrderAdmin` (`src/lib/tr/commerce/customers.ts`) before inserting the order: it finds the customer by e-mail or creates one (adding the delivery address when it is new) and stamps `customer_id`. **This step can never block a sale** — it swallows and logs its own errors, so a missing table or a race just leaves `customer_id` null. The owner can also add customers by hand (**Müşteri Ekle**), which is how customers exist before their first order.

**Pages** (all editor-style except the list): `/musteriler` (`TrOwnerCustomersPage` — search, Filtre popover for orders yes/no and creation date, sortable table, pager; **Dışa Aktar / İçe Aktar** are present but disabled, "Yakında"), `/musteriler/yeni` and `/musteriler/[id]/duzenle` (one form, `TrOwnerCustomerEditPage`: Müşteri Bilgileri, Adres list with an "Adres Ekle" drawer, Müşteri Notları, and a delete card when editing), `/musteriler/[id]` (`TrOwnerCustomerDetailPage`, read-only: header facts, four totals, Not, Adresler, Siparişler table; Önceki / Sonraki walk the list newest-first and give way to **Kapat** when opened from an order). Editor routes are registered in `PANEL_EDITOR_ROUTES`. There is deliberately no timeline, account status, marketing consent, tags or custom fields — the reference admin has them, we don't need them yet.

**Totals are derived, not stored.** `indexCustomerStats` (`src/lib/tr/customers/customerModel.ts`) computes count, spend, average basket, items per order and last order from the cached order list, using the same rules as the dashboard/Raporlar (`orderRevenue.ts`: paid or test, not cancelled/pending/failed; the boutique's own lines net of discount, no shipping). Orders link by `customerId`, falling back to e-mail so orders from before the patch still count. Search folds Turkish case (`searchFold.ts`: İ/I/ı/i all match), shared with the order list.

**API:** `GET/POST /api/tr/owner/customers`, `GET/PATCH/DELETE /api/tr/owner/customers/[id]`; validation in `validateCustomerInput` (name, e-mail, phone, address rules incl. `validateTurkeyShippingAddress`); a duplicate e-mail returns 409 with `existingCustomerId` so the form can offer "Müşteriyi aç"; a missing table returns 503 ("not set up") for the page to show. Client: `fetchOwnerCustomers` / `createOwnerCustomer` / `updateOwnerCustomer` / `deleteOwnerCustomer` in `ownerClient.ts` (cache key `customers:`, invalidated with the order lists).

## Manual orders & drafts (Sipariş Oluştur, Taslaklar)

The owner can build an order by hand — a customer who ordered over Instagram or WhatsApp, an in-person sale — and keep unfinished ones as drafts. The editor copies the reference admin's "Yeni Sipariş Ekle" page. **Apply `supabase/patch_tr_manual_orders.sql`** (needs `patch_tr_customers.sql`; for selling variants also `patch_order_items_variant.sql`) before using it: `tr_orders.channel` (`storefront` | `manual`), `customer_note`, `discount_title`, and the `tr_order_drafts` table. Without the patch the buttons work but saving reports "not set up" (drafts) or fails on insert (orders); the shop's checkout never writes these columns and is unaffected.

**Pages.** `/siparisler/yeni` (a new order) and `/taslaklar/[id]` (a draft) are the *same* editor, `TrManualOrderEditor` (`components/tr/panel/orders/manual/`), reached through `TrOwnerNewOrderPage`; `/taslaklar` is the list (`TrOwnerOrderDraftsPage`: search, sortable table with the note icon and a "Taslak" chip, pager). Siparişler is a nav *group* (Siparişler, Taslaklar) — Taslaklar stays out of the phone tab bar (`tabBar: false`, `panelTabBarItems`). The editor: **Sipariş Detayı** (search opens the "Ürün Ekle" modal; a table with quantity and delete), **Müşteri** (search, "Yeni müşteri ekle", the customer's saved addresses, "Adres Ekle" saves the address onto the customer), **Sipariş Özeti** (Ara Toplam, *Fiyat Azalt*, *Kargo Ekle*, Toplam), **Müşteri Notu**, **Ödeme** (Ödeme bekleniyor / Ödeme alındı). The top bar has **Taslak olarak kaydet** and a ⋮ menu with **Kaydet ve Oluştur** and, for a draft, **Sil**. Nothing is saved until one of those (the panel's manual save model; leaving with edits asks first). `TrPanelModal` is the new shared centered dialog (the drawer stays for forms).

**What can be sold.** The picker lists *units* (`orders/sellableUnits.ts`): a plain product, one size of a product with sizes (its own stock), or one active variant of a Gelişmiş ürün (M7c-1; its own price and stock). Hidden products are not listed; sold-out ones are listed but can't be added. Custom-art boutiques can't create orders by hand (their orders need the customer's photo). No coupon codes: the reduction is **reduce-only**, an amount or a percentage with an optional name, stored as the order's discount with `discount_title`.

**The rules are server-side.** The request names products (product, size, variant, quantity), a customer and one of the customer's address ids; `createManualOrder` (`commerce/manualOrder.ts`) reloads the customer, address and catalog and prices every line itself (`orders/priceManualLine.ts`, pure and tested) — prices and stock are never taken from the client. Stock is **strict** at creation (no overselling; `continue_selling_when_out_of_stock` is not honored) and is taken exactly as for a shop order, through `createOrderAdmin` (new optional inputs `channel`, `customerNote`, `discountTitle`, `customerId`), which also gives it back if the order can't be saved. A hand-made order sends no "new order" push (the owner is the one creating it). "Ödeme alındı" runs `markOrderPaidByOwner` (`commerce/ownerMarkPaid.ts`) — the same steps as the Ödendi button (paid, invoice draft, automatic label for a boutique with a live carrier integration). Drafts hold **no stock and no prices**: `tr_order_drafts` keeps the editor's state (`orders/manualOrder.ts` → `ManualOrderDraft`) plus a list summary, and lines are re-priced from the catalog each time the draft opens; creating the order deletes its draft.

**`channel = 'manual'` in card boutiques.** The shop hides unpaid card checkouts (they are abandoned holds) and never lets the owner mark them paid; a hand-made unpaid order must be visible and markable. So `isActionableOwnerOrder` (list, alerts), the order GET and PATCH routes and the order page's `canMarkPaid` all treat `manual` as an ordinary order. The order page shows "Manuel sipariş", the discount by its name, and a **Müşteri Notu** card.

**Adding a customer mid-order.** "Yeni müşteri ekle" stashes the editor's state in `sessionStorage` (`manualOrderStash.ts`, per tab, tolerant of it failing), opens the customer form with `?from=` the editor, and the customer form returns to it with `?musteri=<id>` (`orders/orderEditorReturn.ts`); the editor then selects that customer and cleans the URL. Coming back any other way restores the stash too.

**API.** `POST /api/tr/owner/orders` (create; optional `draftId`), `GET/POST /api/tr/owner/order-drafts`, `GET/PATCH/DELETE /api/tr/owner/order-drafts/[id]`, `GET /api/tr/owner/product-variants?boutiqueId=` (variants and value labels for the picker). Client: `createOwnerOrder`, `fetchOwnerOrderDrafts` / `createOwnerOrderDraft` / `updateOwnerOrderDraft` / `deleteOwnerOrderDraft`, `fetchOwnerProductVariants` in `ownerClient.ts`.

**Not built.** Etiketler, the price-list dropdown, a per-order invoice type / company details (a hand-made order is Bireysel), editing a *created* order's lines, and a draft-number sequence (a draft goes by the first 8 characters of its id, like an order does).

## Home dashboard (Giriş)

`TrOwnerHomePage.tsx` composes the panel home from `src/components/tr/panel/dashboard/`: a sticky toolbar (date-range menu, "Önceki döneme göre" compare switch, Raporlar link, "Mağazayı aç"), a KPI strip whose selected KPI drives the trend chart and a footer under it that splits that same KPI into fixed slices (Kart ile ödeme, Havale / manuel ödeme, İndirimli siparişler — `TrDashboardKpis.segments`; card and manual add up to the total, discounted orders overlap both), best sellers (products / categories), growth metrics, recent orders, and a floating action pill (orders to ship, manual payments awaiting approval, low stock — dismissible, cycles when there are several). The structure follows the reference admin; colours and the accent are ours. There is no visitor/session analytics in the schema, so those widgets are deliberately absent — Yeni Müşteri, Ödeme Tamamlama Oranı and İptaller stand in for them.

**Data flow.** `GET /api/tr/owner/dashboard?boutiqueId&range[&from&to]` → `ownerDashboard.ts` loads the boutique's orders and products and calls the pure `computeOwnerDashboard` (`dashboardMetrics.ts`). The client reads it through `fetchOwnerDashboard` / `peekOwnerDashboard` in `ownerClient.ts` (cached under `dashboard:` keys, invalidated with the order and product lists). Aggregation is in memory — fine for a boutique's order volume; at tens of thousands of orders replace `ownerDashboard.ts` with SQL aggregation returning the same `TrOwnerDashboard` and the UI does not change.

**Definitions live in one place — the header of `dashboardMetrics.ts` (tests in `dashboardMetrics.test.ts`).** Revenue and order count are paid, non-cancelled, non-test orders; revenue is the boutique's own line total minus its share of the order discount, shipping excluded (the same rule as the Raporlar summary — both use `orderRevenue.ts`). A new customer is one whose first paid order overall (lower-cased email) falls in the window. İptal is an order that was paid and then cancelled. Payment completion exists only for card-enabled boutiques: card-paid ÷ (card-paid + failed + pending checkouts). Card vs manual is decided by whether the order has an iyzico payment id.

**Date ranges** (`dashboardRange.ts`, tests in `dashboardRange.test.ts`) use Europe/Istanbul as a constant UTC+3. Calendar ranges (Bu Hafta / Bu Ay / Bu Yıl…) compare against the same elapsed span of the previous unit; rolling ranges (Son 7 Gün…) compare against the equal-length window before. Bucket size (hour / day / week / month) follows the span. Custom ranges are validated server-side (real dates, not in the future, at most a year).

**Adding a KPI:** add the field to `TrDashboardKpis` and its computation in `dashboardMetrics.ts` (with a test), then add a row to `TR_DASHBOARD_METRICS` in `dashboard/dashboardFormat.ts` if it should drive the chart. A chart KPI must also live on `TrDashboardSegmentKpis` (computed in `summarize`) so the footer can show it per slice. Raporlar (`TrOwnerReportsPage.tsx`) still uses the older `ownerSummary.ts`.

## Checkout & orders

`POST /api/tr/checkout` creates the order; `TrCheckoutPageContent.tsx` drives the checkout page. Supporting logic: `src/lib/tr/cartCheckout.ts`, `checkoutProfile.ts`, `checkoutValidate.ts`, `checkoutSelection.ts`, `orders.ts`, `inventory.ts` (stock decrement — skipped entirely for `custom_art` per capability flag), `discountCodes.ts`. Checkout re-prices and re-validates server-side; it never trusts client-submitted prices.

**Variants (M7c-1).** A Gelişmiş ürün with variants is sold by choosing one: checkout takes an optional `variantId` per line (`CheckoutClientItem`) and requires it when the product has variant rows. `resolveVariantSale` (`src/lib/tr/variants/variantSale.ts`, pure) decides price (the variant's, else the product's), active and stock; the order item stores `variant_id` and a `variant_label` snapshot ("Kırmızı / S", `supabase/patch_order_items_variant.sql`) and `size` stays null. Stock moves on the variant row (`commerce/inventory.ts`: compare-and-set on the variant's stock) and `tr_products.stock` is re-summed from the active variants, so lists and the sold-out state keep working. Every place that takes or returns stock builds its lines with `inventoryLinesOf` (`commerce/inventoryLines.ts`) so cancel, abandoned iyzico holds and re-payment treat variants the same. Screens show the choice through `orderItemOption` ("Varyant: …" or "Beden: …"). The shop itself cannot pick a variant yet (product-page selectors and cart are M7c-2), so only the API sells them; Gelişmiş stays staff-only in the type chooser until then.

Without a live payment integration, checkout creates a **pending** order and the owner marks it paid manually from the panel. `TR_CHECKOUT_SANDBOX` forces this behavior for staging even when a payment integration exists.

## Discount campaigns (İndirimler)

**Status (2026-09-29): M1–M4 are all built — the feature is complete.** `patch_discount_campaigns.sql` is applied in production; **`supabase/patch_discount_campaign_usage.sql` (new, M3) is not yet applied** — Mert needs to run it before an automatic campaign's usage limits actually get enforced (checkout degrades safely without it: the campaign still discounts the cart, it just can't count uses — see M3 notes). The panel has a full editor for both kinds at the **İndirimler** nav entry, replacing the old coupon MVP's UI entirely, and the storefront applies both automatic campaigns and redeemed codes at checkout.

**The model** mirrors ikas: a **campaign** is either `kind: 'automatic'` (applies itself when a cart matches, no code) or `kind: 'code'` (only applies through one of its own codes). Both share the same fields — İndirim Türü (`percent` | `fixed` | `free_shipping`; X Al Y Kazan is not modeled), Koşullar (every product, or a scoped set in `tr_discount_campaign_products`, with an "İndirimli ürünleri dahil et" opt-in for items already on sale), Gereksinimler (optional min/max cart subtotal and item count — checked against the **whole cart**, not the scoped subset), Ayarlar (`stackable`), Aktif Tarihler. Where they differ: an automatic campaign has its own Kullanım Limitleri (`usage_limit_total` / `usage_limit_per_customer` on the campaign row); a code campaign has a **Kuponlar** tab instead — `tr_discount_campaign_codes`, one row per redeemable code, each with its own independent total/per-customer limits. "Otomatik Kod Üret" bulk-inserts several codes sharing one prefix and one set of limits. Per-customer usage is **not** tracked in a new table — `tr_orders` already has `discount_code` and `customer_id`/`customer_email`, so it's counted from there.

**The engine is pure and tested** (`src/lib/tr/discounts/campaignRules.ts`, `codeRules.ts`): `readCampaignBody` validates the shared tabs (amounts arrive as kuruş — the panel form converts TRY before calling it, like the product form does); `campaignMatchesCart` / `campaignDiscountKurus` / `qualifyingSubtotalKurus` decide whether a campaign applies and what it takes off, scoped correctly to its own Koşullar; `resolveAutomaticDiscount` picks which of a boutique's automatic campaigns apply to a cart — **non-stackable campaigns are mutually exclusive (the single largest discount wins), every matching stackable campaign combines with it, each computed independently against its own scope and the total capped at the cart subtotal** (a default, not yet confirmed against real multi-campaign scenarios); `evaluateCodeRedemption` is the code-entry equivalent. `codeRules.ts` has the Kuponlar-tab validation and `generateCampaignCodes` (`<prefix><6 random lowercase alphanumeric chars>`, collision-checked against a passed-in existing set).

**All four milestones are built:**

| # | Scope | Touches checkout? |
|---|---|---|
| M1 | Schema (`tr_discount_campaigns`, `tr_discount_campaign_products`, `tr_discount_campaign_codes`) + types + the pure engine above | No — **built** |
| M2 | Panel: Kampanyalar list, "Kampanya Ekle" type chooser, the shared editor tabs for `kind: 'automatic'`; DB layer (`catalog/discountCampaigns.ts`) and owner API routes | No — **built** |
| M3 | Checkout: evaluate automatic campaigns against the cart (`checkoutValidate.ts`), apply the M1 stacking rule | **Yes — built.** Mert explicitly lifted the freeze for this scope (same exception pattern as M7c-1). |
| M4 | Panel + DB for `kind: 'code'` (the Kuponlar tab, both add-a-code modes) and pointing checkout's existing code lookup at the new tables instead of the retired `tr_discount_codes` | **Yes — built.** Mert lifted the freeze again immediately after M3. |

**M3 notes.** `resolveCheckoutFromCatalog` (`checkoutValidate.ts`) now, after the existing code-discount block, loads the boutique's `kind: 'automatic'` campaigns (`listAutomaticCampaigns`), builds a `DiscountCartContext` from the resolved lines (`onSale` computed from each line's product `compareAtPriceKurus`), drops any campaign the customer (by email) is already over its Müşteri başına kullanım limiti for (`excludeCampaignsAtCustomerLimit` → `countCustomerCampaignUses`), then calls `resolveAutomaticDiscount` — so the M1 stacking rule decides what applies, checkout just supplies the cart and the customer filter. The result adds to (not replaces) any manual-code discount, both capped together at the cart subtotal; a `free_shipping` campaign zeroes the quoted shipping fee; `discountTitle` becomes the applied campaigns' titles joined with ", " (shown on the order instead of the generic "İndirim" label, `TrOrderSideCards.tsx`'s existing `discountLabel` already prefers it).

Two schema-dependent pieces needed `patch_discount_campaign_usage.sql` (new, adds `tr_orders.discount_campaign_ids uuid[]`, not yet applied): burning **Toplam kullanım limiti** only once payment succeeds (`incrementCampaignUsage`, mirroring `incrementDiscountCodeUsageAdmin` exactly — a compare-and-set on `used_count`, called from the checkout route's sandbox path and from `capturePaidOrder.ts` for iyzico) and counting a customer's prior uses for **Müşteri başına kullanım limiti** (`countCustomerCampaignUses`, a `discount_campaign_ids @> [id]` containment query). Both degrade tolerantly without the column — `createOrderAdmin` tries the insert with `discount_campaign_ids`, and on a schema-missing error retries without it, so a campaign still discounts every cart even before the patch is applied; it just can't yet block on Toplam/Müşteri başına limits (they'd need a real order history against the new column to count against). `TrOrder`/`mapOrderRow` were deliberately left untouched — `getOrderDiscountCampaignIdsAdmin` is a narrow raw-column read used only by `capturePaidOrder.ts`, so nothing else takes on the new column.

**M4 notes.** The Kuponlar tab (`TrCampaignCouponsCard.tsx` + `TrCampaignAddCodeModal.tsx`) only shows once a `kind: 'code'` campaign is saved — codes belong to a campaign id, so a brand-new one shows a "kaydedin önce" hint instead. Codes add/delete **instantly** through their own API (`catalog/discountCampaignCodes.ts`, `/api/tr/owner/discount-campaigns/[id]/codes[/…]`), not through the campaign's own Kaydet — same pattern as a category's image upload. The editor's fifth tab swaps between Kullanım Limitleri (automatic) and Kuponlar (code) based on `form.kind`; `kind` itself is chosen once at "Kampanya Ekle" (`TrCampaignTypeChooser` now enables both cards) and isn't editable afterward — the type-chooser passes it via `?kind=code` on the "yeni" route, read by `TrOwnerDiscountCampaignEditorPage`.

Checkout's discount-code path (`checkoutValidate.ts`) now looks up `tr_discount_campaign_codes` + its parent campaign and runs `evaluateCodeRedemption` (the M1 pure engine), instead of the old `tr_discount_codes` lookup — that whole block (`getDiscountCodeForBoutiqueAdmin`, `incrementDiscountCodeUsageAdmin`, `computeDiscountKurus`) is gone from checkout. A code's own Müşteri başına kullanım limiti reuses the **existing** `tr_orders.discount_code` column (no schema addition needed there, unlike automatic campaigns) — `countCustomerCodeUses` counts a customer's non-failed/refunded orders with that exact code. Codes are stored **lowercase** (`codeRules.ts`'s `normalizeCode`, a deliberate M1 departure from the old system's uppercase), so `createOrderAdmin` no longer uppercases `discountCode` on the way in — it stores exactly what checkout resolved. A code's discount and an automatic campaign's discount are independent and always additive (capped together at the cart subtotal) — a code campaign's own `stackable` flag is validated and stored but **not yet read by checkout**; it doesn't compete for the "one non-stackable source wins" slot the way automatic-vs-automatic does in `resolveAutomaticDiscount`. That's a real gap, same kind as the still-unconfirmed automatic stacking default — flag it if a code needs to be mutually exclusive with automatic campaigns.

`src/lib/tr/commerce/discountCodes.ts` (the old `tr_discount_codes` admin CRUD) is now **dead except for one caller**: `src/app/api/tr/admin/seed/route.ts`'s `discountCodes` seed input still calls `createDiscountCodeAdmin`, so seeded codes go into a table checkout no longer reads — seeding one now produces an inert row, not a working coupon. Left as-is rather than touched, since the seed script is a dev utility, not user-facing; a future pass could point it at `addCustomCode` (`discountCampaignCodes.ts`) instead, or the file/table could be dropped outright once nobody minds losing the old data shape.

**M2 notes.** `TrOwnerCampaignsPage.tsx` was rewritten in place (same route, same export, so the İndirimler nav entry needed no change): a Kampanyalar list (fetches `tr_discount_campaigns` via the new API), a "Kampanya Ekle" modal (`TrCampaignTypeChooser`) offering Otomatik İndirim (→ the new editor) and a disabled İndirim Kodu card ("Yakında", M4), plus the pre-existing "Ürün indirimleri" (compare-at-price) section carried over unchanged — that's a separate, older feature (per-product sale price) that the campaigns model doesn't replace. The editor (`TrDiscountCampaignEditor.tsx`, at `/tr/panel/kampanyalar/yeni` and `/tr/panel/kampanyalar/[id]`, both full-screen editor routes) covers all six shared tabs for `kind: 'automatic'` only; `kind: 'code'` campaigns can't be created yet. The old coupon MVP (`discountCodes.ts`, `tr_discount_codes`) is now fully unreached from the panel (no remaining nav or UI touches it) but not deleted — left alone until M4 confirms nothing else needs it. Koşullar's "Belirli Ürünler" scope uses a new `TrCampaignProductPicker` modal + `useOwnerProducts` hook (product-level, not variant-level, since a campaign's scope is `productIds`).

## Shipping

**What the shopper pays** is per-boutique DB config, not code: `tr_boutiques.shipping_fee_kurus` (flat fee, 0 = no shipping charge), plus at most one free-shipping threshold — `free_shipping_min_items` (order has N+ items) or `free_shipping_min_subtotal_kurus` (items subtotal, before discounts, reaches N). They are on `tr_boutiques_public` because the cart/checkout/PDP show them. `src/lib/tr/shipping/quoteShipping.ts` turns a boutique's `ShippingFeeConfig` plus the cart lines into a fee; `shippingCopy.ts` builds every piece of shopper-facing shipping text from the same config so it can't drift from what is charged; `settings.ts` validates writes. The server re-quotes from the re-priced catalog lines in `POST /api/tr/checkout` — the client-side numbers are display only. Set it through the intake file (`shippingFeeTry`, `freeShippingMinItems` | `freeShippingMinSubtotalTry`), `PATCH /api/tr/owner/boutiques/[id]`, or the seed route. A boutique with no fee set charges no shipping — `scripts/create-boutique.mts` warns when the intake omits it. `quoteShipping.test.ts` (run `npm test`) pins lilabutik's exact rules (120 TL, free at 2+ items) and the shopper-facing copy. The rule is identical for every product in the cart. There is **no per-product shipping exception** — one existed (`midiJeanTwins.ts`, hardcoding free shipping for two specific dresses) and was deleted because it was a core-code-reaching-into-a-specific-product violation. If a future promo needs product-specific shipping behavior, it needs a generic DB-backed mechanism, not a name/id match in this file.

**The carrier integration is a separate thing.** `src/lib/tr/shipping/registry.ts` (`SHIPPING_BY_SLUG`, `boutiqueHasCarrierIntegration()`) still gates which boutiques have a live Basit Kargo integration (label purchase, tracking) — currently just `lilabutik`, and it is still a per-slug code touch (roadmap P4-T2 moves it to per-boutique credentials). Boutiques without one use their own carrier: the owner updates the order status by hand (there is no tracking-code entry yet — roadmap P4-T3). `AUTO_BUY_FEE_CAP_KURUS` (`shipping/types.ts`) is the carrier label spend cap and is likewise Lila-only until P4-T2. Basit Kargo webhook: `src/app/api/tr/shipping/basitkargo/webhook/route.ts`.

## Payments (iyzico)

`src/lib/tr/payments/registry.ts` is the read path for "does this boutique take card payments and with what credentials" — `boutiqueOffersIyzicoCheckout()`, `getIyzicoBuyerProtection()`, `getIyzicoCredentials()`. Purely DB-backed: reads `tr_boutique_integrations` (credentials AES-256-GCM encrypted via `credentialEncryption.ts`) and returns `null`/`false` if no row exists. There is no env-var fallback — that legacy path (`IYZICO_CHECKOUT_SLUGS`, `IYZICO_BUYER_PROTECTION_BY_SLUG`, `CREDENTIAL_ENV_BY_SLUG`) was removed once lilabutik's real credentials were migrated into the table and verified against live production checkout (2026-09-23). A boutique with no `tr_boutique_integrations` row simply doesn't offer iyzico checkout — that's not a bug to route around, it's the correct state until someone adds a row (`scripts/migrate-lilabutik-iyzico-credentials.mts` is a worked example of how, though it's slug-specific and would need generalizing for a second boutique).

**Owners connect their own iyzico account in the panel** (Ayarlar → Kart ödemesi, built 2026-10-16): `TrOwnerIyzicoCard.tsx` → `PUT/GET/DELETE /api/tr/owner/boutiques/[id]/iyzico` → `payments/iyzicoConnection.ts`. The owner pastes the API key and the güvenlik (secret) key; the server checks them with iyzico (`iyzicoCheckCredentials`; keys beginning `sandbox-` go to the sandbox host, anything else to live), stores them AES-256-GCM encrypted in `tr_boutique_integrations` (an existing row keeps its other settings, e.g. the buyer-protection badge) and read-backs them. The panel only ever sees the last four characters of the API key; no key is returned, logged or put in an error message, the route answers `no-store`, and connecting is rate limited (8 per 15 min per store and user). A wrong key is a 422 with iyzico's own message and nothing is stored. "Bağlantıyı kaldır" switches card payments off and clears the keys. Pure rules and tests: `payments/iyzicoKeys.ts`. This replaces handing keys to Mert, but the script below still works.

**The same thing from a terminal** (a client who has their own merchant account): `scripts/set-boutique-iyzico-credentials.mts` — generic, takes `--slug`, prompts for the two keys at a hidden prompt (never as arguments, never printed), checks them against iyzico (`iyzicoCheckCredentials` in `iyzicoClient.ts`; sandbox and live keys differ), encrypts, writes the `tr_boutique_integrations` row, reads it back the way checkout will. The header comment of the script is the runbook (`vercel env pull` → `--dry-run` → write → delete the env file). **Whoever holds the client's keys runs it** — keep live keys out of chat and out of agent sessions.

Checkout iyzico flow: `src/app/api/tr/checkout/iyzico/{start,abandon,callback}/route.ts`.

## Order e-mails

`src/lib/tr/orderMail/` — `templates.ts` (pure HTML/text builders, reusing the auth-mail shell and `escapeHtml`), `mapOrder.ts` (order row → template input, pure), `sendOrderEmails.ts` (fire-and-forget senders). A **customer confirmation** goes out once an order is paid (`capturePaidOrder.ts` for iyzico; the checkout route for non-iyzico/sandbox orders), and the **owner gets a "yeni sipariş" mail** next to the existing web push (`orders.ts#createOrderAdmin`, dynamic import after the push). They send through `sendPlatformEmail` (Resend, `RESEND_API_KEY`) from `noreply@cortisstyle.com` with the **store name as display name** and the store's contact e-mail as `replyTo` — so a client's replies reach the client, not the platform. Failures are swallowed and logged: an order must never fail because a mail did. There is no "kargoya verildi" mail yet.

## Conversion tracking & cookie consent

Per-boutique ad/analytics tags live in `tr_boutiques.tracking` (jsonb; `TrBoutiqueTracking` in `types/tr-marketplace.ts`; set in Ayarlar → *Reklam ve analiz*, in the intake as `tracking`, or by `updateBoutiqueBrandAdmin`). Supported: GTM container, GA4 measurement id, Meta pixel, Google Ads conversion (`AW-…` + label). Pure, tested logic is in `src/lib/tr/tracking/` (`config.ts` validation/normalisation, `events.ts` GA4/Meta/Ads event shapes, `consent.ts`, `items.ts` cart-line → item, `runtime.ts` loader + dispatcher). Components: `TrBoutiqueTracker` (mounted in the editorial shell; injects scripts only after consent), `TrTrackingEvents` (`TrTrackViewItem` on the PDP, `TrPurchaseTracker` on `siparis-onay` for paid, non-sandbox orders — de-duplicated per order). Events: `page_view`, `view_item`, `add_to_cart` (cart store), `begin_checkout`, `purchase`. **Nothing loads until the visitor chooses "Tümünü kabul et"** in `TrBoutiqueCookieNotice` (choices: *Yalnızca zorunlu* / *Tümünü kabul et*; storage key `cortis-tr-boutique-cookie-consent`; a boutique with no tracking configured keeps the old info-only banner). With a `gtmId` set, `loadTrackingTags` skips the direct GA4/Google Ads loading (GTM carries those; events go to `dataLayer` in GA4 shape) but still loads the Meta pixel directly — don't also add the Meta pixel inside GTM or it counts twice.

## Company details (künye / legal pages)

`tr_boutiques` also carries `vergi_dairesi`, `mersis_no`, `kep_address` (with `vergi_no`, `legal_name`, `physical_address`), edited in Ayarlar and rendered by `legal/docs.ts` on the künye, mesafeli satış, ön bilgilendirme and KVKK pages. `src/lib/tr/company.ts` normalises/validates the new ones (vergi dairesi ≤ 80 chars, MERSİS exactly 16 digits, KEP and contact e-mail shape); `vergi_no` is stored as typed. All of this — plus the tracking column — arrives with **`supabase/patch_tr_boutiques_company_and_tracking.sql`** (one transaction, also recreates `tr_boutiques_public`; Mert applies it). Until it is applied every read/write here is tolerant: `updateBoutiqueBrandAdmin` retries without the new columns and only throws if a non-empty new value was actually entered.
